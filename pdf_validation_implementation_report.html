既存のPowerShell（.ps1）によるWord・PowerPoint開封検査に対し、PDFの破損・開封パスワード・セキュリティ警告を検知する機能を追加するための方式比較と実装方針。

作成日：2026年11月9日対象環境：Windows / PowerShell検討方式：3方式
EXECUTIVE SUMMARY
結論：ハイブリッド方式を推奨

PDFについても既存のOffice検査と同様に、実際にPDFビューアを起動して警告・ポップアップを検知できる。ただし、PDFの構造的な正常性と実際のビューアにおける開封結果は異なるため、qpdfによる構造・暗号化検査と、Adobe Acrobat等を使ったUI検査を組み合わせる構成が適している。

既存のツールは、.ps1スクリプトからWord・PowerPointを1ファイルずつ開き、アラートやポップアップの有無を監視する方式で構築されている。本レポートは、この考え方をPDFへ拡張する際の実現方式、検知範囲、サンプルコード、運用上の注意点を整理したものである。

1. 実現方式の比較

PDFの検査は「ファイルそのものの解析」と「実際のPDFビューアでの動作確認」に大別できる。目的に応じて、以下の3方式から選択する。

方式概要特徴・適合性
① PDFビューア起動方式Adobe AcrobatなどでPDFを開き、警告・ポップアップを監視既存のOffice検査方式に最も近い
② PDF解析ツール方式qpdf等により構造上の問題、暗号化、パスワード要求を判定GUI不要で比較的安定・高速
③ ハイブリッド方式 推奨解析を先に実施し、必要なケースにビューア検査を追加異常の分類と実利用環境での再現性を両立

検知できる内容の違い

検知対象① ビューア起動② PDF解析
PDFファイルの破損○◎
開封パスワードの要求◎◎
暗号化・操作権限の制限○◎
Acrobat固有のセキュリティ警告◎×
保護されたビュー等の警告バー◎×
JavaScript・外部アクセス警告◎△（関連要素の構造解析は可能）
ページが実際に表示できるか◎△（レンダリング検査併用で○）

※ ◎：得意、○：対応可能、△：一部対応、×：対象外。実際の検知可否は、使用ビューア、バージョン、セキュリティ設定、検知実装に依存する。

重要：「PDFとして正常であること」と「利用者環境で警告なく開けること」は同義ではない。正常なPDFでもビューアの設定により警告が生じ、軽微な構造不整合があってもビューアが自動修復して表示できる場合がある。

2. 方式① Adobe Acrobatを起動して検知する

既存のWord・PowerPoint検査コードを最大限流用したい場合に適した方式。PowerShellからAdobe Acrobat/Readerを起動し、Windows UI Automation等でダイアログや文書画面内の警告要素を調査する。

PowerShell（.ps1）PDFのパスを指定、1ファイルずつ処理
↓
Adobe Acrobat / Reader 起動対象PDFを開く
↓
Windows UI Automationによる監視ダイアログ・警告バー・表示状態を確認
↓
正常警告がなく文書を表示
警告あり・開封失敗内容を分類して記録

PowerShellによる起動例

PowerShell｜Acrobat起動例
$pdfPath = "C:\work\sample.pdf"
$acrobat = "C:\Program Files\Adobe\Acrobat DC\Acrobat\Acrobat.exe"

Start-Process `
    -FilePath $acrobat `
    -ArgumentList @(
        "/n",
        "/s",
        "`"$pdfPath`""
    )

上記は起動の概念を示した例であり、Acrobat.exeの配置場所は製品・インストール構成によって異なる。/nや/s等のスイッチはバージョン依存・正式サポート外の扱いがあるため、対象環境で検証する必要がある。

検知対象の例

  • 開封パスワードの入力ダイアログ
  • 破損・形式不正等による開封エラーダイアログ
  • セキュリティ警告ダイアログ、外部通信の確認
  • 文書画面内の黄色・赤色の警告バー
  • 文書が表示されたか、一定時間内に開封処理が完了したか
実装上の注意：警告は独立したウィンドウだけとは限らない。Acrobatのメインウィンドウ内に表示される警告バーも検査すること。また、Acrobatが既存プロセスを再利用する場合があるため、起動直後のPIDだけで対象文書を特定しない設計が望ましい。

Windows UI Automationでの検知には、原則として操作可能な対話型デスクトップセッションが必要となる。非対話型Windowsサービス、画面のない実行環境では同一手法が機能しない場合がある。

3. 方式② qpdfでPDFを解析する

qpdfはPDFの内部構造や暗号化状態を扱えるコマンドラインツール。PowerShellから呼び出し、終了コードや標準エラー出力を基に機械判定できる。

① PDFの構造検査

PowerShell｜構造検査
qpdf --check "C:\work\sample.pdf"
終了コード判定
0構造上の問題が検出されなかった
2エラーが検出された
3警告が検出された（修復可能な問題など）

② 開封パスワード要求の確認

PowerShell｜パスワード判定
qpdf --requires-password "C:\work\sample.pdf"
終了コード扱い方の目安
0開封にパスワードが必要
2パスワードなしで開ける状態（暗号化の有無は別途確認）
3指定されたパスワードで開ける暗号化PDF等（qpdfのバージョン・条件に応じて確認）

※ 終了コードはqpdfのバージョン・オプション・エラーの種類に依存するため、導入時に採用バージョンの公式マニュアルとテストファイルで照合する。--requires-password単独では破損判定や権限制限の網羅的判定はできない。

PowerShell実装例（簡易サンプル）

qpdfがインストールされ、PATHから実行できることを前提に、パスワード要求と構造検査を組み合わせた例を示す。

PowerShell｜Test-PdfFile
function Test-PdfFile {
    param(
        [Parameter(Mandatory)]
        [string]$PdfPath
    )

    $pdf = (Resolve-Path -LiteralPath $PdfPath -ErrorAction Stop).ProviderPath

    # 開封パスワード要求の確認
    $null = & qpdf --requires-password $pdf 2>&1
    $passwordCode = $LASTEXITCODE

    if ($passwordCode -eq 0) {
        return [PSCustomObject]@{
            File   = $pdf
            Status = "PASSWORD_REQUIRED"
            Detail = "構造検査は未実施"
        }
    }

    if ($passwordCode -notin @(2, 3)) {
        return [PSCustomObject]@{
            File   = $pdf
            Status = "UNKNOWN"
            Detail = "パスワード検査で想定外の終了コード"
        }
    }

    # PDF構造の検査
    $log = (& qpdf --check $pdf 2>&1 | Out-String)
    $code = $LASTEXITCODE

    $status = switch ($code) {
        0 { "OK" }
        2 { "ERROR" }
        3 { "WARNING" }
        default { "UNKNOWN" }
    }

    return [PSCustomObject]@{
        File                 = $pdf
        Status               = $status
        PasswordCheckCode    = $passwordCode
        Detail               = $log.Trim()
    }
}

Test-PdfFile -PdfPath "C:\work\sample.pdf"
判定範囲の限界：qpdf --checkは主にPDF構造を検査するものであり、全ページが正しく描画されることまで保証しない。必要に応じてMuPDF / mutoolの全ページレンダリング検査を追加する。

4. 方式③ ハイブリッド方式（推奨）

既存のOfficeファイル検査に近い判定体系を保ちながら、PDF固有の暗号化・構造異常を精密に分類する構成である。解析で明確な異常を特定できたケースは、その時点で結果を記録し、必要なケースのみビューアで実検査する。

検査対象：sample.pdfファイル存在確認、拡張子・検査IDの付与
↓
Step 1：qpdfによる事前検査破損・パスワード要求・暗号化状態を確認
↓
異常・要確認
結果を記録ERROR / WARNING / PASSWORD_REQUIRED
構造検査OK
Step 2：Acrobat起動警告・ダイアログ・文書表示を監視
↓
Step 3：結果を統合・出力CSV / JSON / 既存の検査結果フォーマット

出力結果の例

ファイル構造検査開封パスワードAcrobat警告最終判定
A.pdfOK不要なし正常
B.pdfERROR不要未実施破損疑い
C.pdf未実施必要未実施開封制限
D.pdfOK不要あり要確認

運用上は、最終判定とは別に、ParserStatus、PasswordStatus、ViewerStatus、WarningType、LogPathを保持すると、原因調査や再検査が容易になる。

5. 実装・運用上の注意点

検査の信頼性

起動タイムアウト、ウィンドウ監視、終了処理、再試行、ログ保存を設計する。

セキュリティ

外部由来PDFは隔離環境で扱い、ビューアの保護機能を無効化しない。

判定の透明性

検査不能・タイムアウトは正常扱いにせず、UNKNOWNとして記録する。

セキュリティ設定の分類

  • 開封パスワード：文書を読むためのパスワード。開封を妨げるため、異常または要対応として扱いやすい。
  • 権限制限：印刷・編集・コピーなどを制限する設定。閲覧自体はできる場合があるため、開封失敗と同一視しない。
  • 証明書保護・組織ポリシー：証明書、保護設定、ビューア環境等によって開封や操作の可否が変わる場合がある。
  • ビューア固有の警告：信頼済み設定、保護されたビュー、JavaScript・外部アクセス設定など、実行環境の影響を受ける。

既存.ps1に組み込む際のチェックポイント

  1. 検査端末のAcrobat/Reader製品名、バージョン、実行ファイルパスを固定・記録する。
  2. 対話型セッションを確保し、検査ファイルごとに前回の表示状態が残らないよう制御する。
  3. 同じ異常でも、PDF構造異常か、ビューア・環境依存の異常かを区別して出力する。
  4. 1ファイルあたりのタイムアウトと、異常終了時のプロセス・ウィンドウ後始末を定義する。
  5. パスワード付きPDF、部分破損PDF、警告バーが出るPDF、正常PDFを含むテストセットで検証する。
留意：PDFの自動開封は、JavaScript、外部リンク、埋め込みコンテンツ等に起因するリスクを伴う。信頼できないファイルは隔離された検査VM等で開封し、ネットワーク・権限を最小化すること。

6. 要件確認と次のステップ

最適な検査構成を確定するため、まず既存ツールでの「異常」の定義を明確にする。

検査要件の候補推奨実装
開けないPDFのみを異常とするqpdfによる事前検査＋必要時の表示確認。UI監視は限定的に利用。
開けても警告・ポップアップが出たら異常とするqpdf＋AcrobatのUI Automation監視を組み合わせる。
特定の警告だけを異常とする対象警告の文言・UI要素・バージョン差を整理してルール化する。

次の検討事項：検査対象のPDFビューア（Acrobat / Reader / Edge等）、PowerShellの実行形態（ログオンセッション / タスクスケジューラ / サービス）、想定ファイル数、異常判定ルール、既存ログの形式を確認した上で、.ps1の詳細設計に進む。
